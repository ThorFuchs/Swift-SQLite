# Security policy

## Supported versions

| Version | Supported |
| --- | --- |
| Latest minor release of the current major version | Yes |
| Older releases | No; please upgrade |

Before 1.0.0, only the latest 0.x release is supported.

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub:
**Security → Report a vulnerability** on
[github.com/ThorFuchs/Swift-SQLite](https://github.com/ThorFuchs/Swift-SQLite/security/advisories/new).
Don't open a public issue for a vulnerability.

Include the affected version, the platform (macOS, iOS or Linux), and the smallest
code or database file that shows the problem. We aim to acknowledge a report within
seven days and to agree a disclosure date with you once a fix is available.

## Scope

- **This package:** connection handling, transaction control, limits, bounds checks,
  SQL generated by helpers (identifiers, predicates, compare-and-set, pagination).
- **The SQLite engine on Linux:** the vendored amalgamation in
  `Sources/CSQLiteSwift`. Engine vulnerabilities are fixed upstream by the SQLite
  project; we ship the fixed amalgamation in a patch release
  ([provenance](Sources/CSQLiteSwift/PROVENANCE.md)).
- **The SQLite engine on Apple platforms** is the system library and is updated by
  Apple with the operating system. Report those to Apple.

## Hardening defaults

SQLiteSwift binds every value as a parameter, quotes identifiers, refuses multiple
statements where one is expected, denies transaction control from user SQL, turns
`trusted_schema` off, caps value sizes with `SQLITE_LIMIT_LENGTH`, and bounds every
read. Treat SQL text itself as code: never build it from untrusted input.
